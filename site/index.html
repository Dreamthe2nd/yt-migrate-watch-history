▶ yt-migrate-watch-history
How it works Prerequisites Setup Usage Reference

Python 3 · Playwright · sqlite3 — one file, zero framework

Replay your entire YouTube watch history — one video at a time.

migrate_watch_history.py replays every video in scraped_history.json — the sole input — in reverse order, dwells a randomized 20–45 seconds on each page, and commits every completion to a local SQLite database before the next video starts. Log in once with your own Google Chrome; playback then runs in Playwright's muted Chromium, which recycles itself every 50 videos so RAM and CPU stay flat for days. Stop it at any moment — even a system shutdown — and it automatically resumes from the next video.

01 · Pipeline

How it works

Two browser stages, then a five-step loop executed once per URL in strict order.

🖥️ Stage 1 — Login in your Chrome

On a fresh run (0 completed videos), the script opens Google Chrome itself (channel="chrome") on the shared ./chrome_profile folder. You sign in to YouTube there — with your real, already-authenticated Chrome profile habits and extensions — confirm in the terminal, and Chrome closes. If Chrome isn't installed, it falls back to Chromium for this one-time step.

🎬 Stage 2 — Playback in Playwright Chromium

The multi-day replay runs in Playwright's bundled Chromium, launched muted (--mute-audio) on the same ./chrome_profile — so it inherits your Chrome login without touching your everyday browser. Your real Chrome stays yours; automation stays isolated.

  1. 1

    Load & reverse — the sole input

    Reads scraped_history.json (a JSON array of full video URLs), trims whitespace, and reverses the array so videos are processed from the original last index down to the first — index -1 → 0. This file is the only data source; the script never generates, samples, or fabricates history. (scraped_history.example.json is a shape reference for humans — it is never read by the script.)

  2. 2

    Skip what's already done — automatic resume

    Every URL is checked against state.db before visiting. Because each watch is committed the moment it finishes, any closure — Ctrl+C, SIGTERM, crash, power loss, routine shutdown — means the next run simply skips everything recorded and starts from the next unwatched video, with zero manual bookkeeping.

  3. 3

    Watch the page

    Navigates with wait_until="domcontentloaded" (60 s timeout), waits up to 5 s for the <video> element, injects a small JS snippet that starts playback if the player is paused, then dwells for a randomized 20–45 seconds.

  4. 4

    Commit immediately — before anything else

    The instant the dwell completes — success or failure — the URL is inserted into watched_videos and conn.commit() runs before the next URL starts. A crash can never lose more than one in-flight view; this commit is what powers "automatically start from the next video" on every kind of closure.

  5. 5

    Refresh the browser — per video and every 50

    After each commit the page is unloaded to about:blank (frees that video's buffers immediately), and every 50 watched videos the entire Chromium process is torn down and relaunched on the same profile (> Browser recycled after 50 videos (RAM/CPU reset).) — so memory and CPU never creep upward over a multi-day run. The login survives every recycle untouched.

Key reliability decisions

  • Chrome logs in, Chromium playsAuthentication happens once in your real Google Chrome (channel="chrome"); the long-running automation is a separate, muted Playwright Chromium on the shared profile — never your daily browser.
  • Commit before the next navigationEvery finished (or failed) URL is in state.db before the loop moves on — unexpected or routine closure always resumes at the next unwatched video.
  • Full browser recycle every 50 videosLong Chromium runs leak memory; periodic relaunch keeps RAM/CPU flat. Per-video about:blank unload drops buffers between navigations. Tune via BROWSER_RESTART_EVERY.
  • domcontentloaded, never networkidleYouTube streaming and telemetry sockets stay open indefinitely — networkidle would hang and time out on essentially every video.
  • --mute-audio at browser launchViews register without sound or notifications; a muted player is also what browsers allow to autoplay.
  • Per-URL try/exceptOne removed video, region block, or transient network error logs a warning and marks the URL as attempted instead of killing a multi-day run.
  • Random 20–45 s dwellLong enough for YouTube to treat each video as genuinely watched, randomized so the rhythm doesn't look mechanical.

02 · Install

Prerequisites & installation

Python 3.10+ and one command. The installer does everything else.

Requirements

  • Python 3.10 or newer — 3.11 / 3.12 recommended
  • Google Chrome (recommended) — used for the one-time login; if absent, the script falls back to Chromium for that step
  • A desktop session — first run needs a visible browser window for the manual YouTube login
  • Steady internet + a machine you can leave on — the full 18,453-video migration runs for several days

Linux only: Chromium also needs a few system libraries — the installer handles them via playwright install-deps.

Install — one command

Linux / macOS
./install.sh
Windows
install.bat

Creates .venv, installs playwright from requirements.txt, downloads the bundled Chromium, and on Linux also installs the system libraries. Done in one shot.

Manual equivalent (if you prefer)

terminal
python3 --version        # 3.10 or newer

python3 -m venv .venv
source .venv/bin/activate    # Windows: .venv\Scripts\activate

pip install -r requirements.txt
playwright install chromium
# Linux only, once — installs system libraries (needs sudo):
# playwright install-deps chromium

Three things: your data file, the two-stage first run, and the artifacts it creates.

Step 1 — Place scraped_history.json next to the script

The input is a plain JSON array of full video URLs, one item per video. Paths are resolved relative to the script, so the file must sit in the same directory as migrate_watch_history.py. Your file contains 18,453 entries. Duplicates are harmless — the primary key keeps them in the state store exactly once. This file is the script's sole input — nothing else is read, and no data is ever invented.

How to use

Telemetry format: [Current/Total] | Watched Xs | Remaining: Y | ETA: ~Z hours, plus a > Browser recycled after 50 videos line at each refresh. The ETA is computed from the observed average per-watch time (dwell + navigation overhead), falling back to the 32.5 s dwell midpoint until the first view completes.

Stop & resume — any closure

Ctrl+C, a crash, power loss, or a routine system shutdown (SIGTERM) all take the same path: every finished view is already committed. Re-run later:

later
python migrate_watch_history.py
# -> "Resuming run: N URLs already recorded
#     - starting from the next unwatched video."

Retry a failed URL

Failed URLs are marked as attempted (committed) on purpose — one dead link must never stall a multi-day run. To replay one, delete its row and re-run:

terminal
sqlite3 state.db "DELETE FROM watched_videos
WHERE url = 'https://www.youtube.com/watch?v=...';\"

Re-run after completion

When the list is exhausted, every URL hits the skip path, so a re-run finishes in seconds and confirms the final count:

terminal
Done. 18453/18453 URLs recorded in state.db.

05 · Reference

Runtime, schema & design

The numbers, the state store, and the architecture rules the script follows.

Runtime estimate — 18,453 videos

ScenarioDwellWall time (dwell only)With overhead
Fastest20 s every video≈ 102.5 h (4.3 days)≈ 5 days
Typical32.5 s average≈ 166.6 h (7.0 days)≈ 8–9 days
Slowest45 s every video≈ 230.7 h (9.6 days)≈ 11 days

Overhead = navigation (~1–3 s) + up to 5 s player wait per video, amortized across the periodic 50-video browser recycles. Skips cost ~0 s. Plan to leave the machine on for roughly a week, powered and with the screen unlocked or a screensaver that doesn't kill the browser.

State schema

state.db — sqlite3
CREATE TABLE IF NOT EXISTS watched_videos (
  url        TEXT PRIMARY KEY,
  watched_at TIMESTAMP
);
-- per video, committed immediately after the dwell:
INSERT OR IGNORE INTO watched_videos (url, watched_at)
VALUES (?, '2026-09-24T07:41:05+00:00');

Idempotency comes from the primary key + INSERT OR IGNORE, plus the pre-visit lookup that skips recorded URLs before the browser even opens a tab. Fixed schema — no extra tables or columns.

Browser lifecycle

refresh policy
# Stage 1 (once): your Google Chrome
launch_persistent_context(
  user_data_dir="./chrome_profile",
  channel="chrome", headless=False)

# Stage 2: Playwright Chromium, muted
launch_persistent_context(
  user_data_dir="./chrome_profile",
  args=["--mute-audio"], headless=False)

# after every commit:
page.goto("about:blank")
# every 50 watched videos:
context.close(); relaunch()  # > Browser recycled...

Both stages share ./chrome_profile, so login persists across recycles. SIGTERM (routine/system shutdown) is routed to the same cleanup path as Ctrl+C.

Architecture rules

⛔ What it is not

  • No classes, no frameworks, no ORM
  • No external dependency beyond playwright — the rest is stdlib (json, sqlite3, random, time, signal, pathlib)
  • No fabricated data — scraped_history.json is the sole input; the example file is never read

✅ What it is

  • One ~250-line file, readable top to bottom
  • Idempotent by construction: every re-run (after any closure) resumes at the next video
  • Failure-isolated: the loop can never die on a single URL
  • Memory-safe over days: per-video unload + full recycle every 50 videos

FAQ

Why does login use Chrome but playback use Chromium?

Your real Google Chrome is where you're already authenticated (and where Google trusts the browser most — extensions, profile history, cookies). Stage 1 lets you sign in there once, on a dedicated shared profile. Stage 2's long unattended run then happens in Playwright's bundled Chromium — a separate, controlled, muted browser — so automation never disturbs your everyday Chrome and vice versa. The shared ./chrome_profile folder carries the session from one to the other. If Chrome isn't installed, Stage 1 falls back to Chromium.

Why is the browser refreshed frequently?

Multi-day Chromium sessions slowly accumulate RAM and CPU overhead (media buffers, renderer processes, internal caches). Unloading each page to about:blank after its commit releases per-video memory immediately, and fully recycling the browser process every 50 watched videos resets everything else — keeping the machine healthy for the whole ~1-week run. Because the profile is persistent, each recycle comes back already logged in.

What happens if the system shuts down or the script is killed?

Nothing is lost. Each URL is committed to state.db the moment its watch completes, SIGTERM is handled like Ctrl+C (clean browser close + a resume hint), and even a hard kill only risks the single in-flight video. The next run skips all recorded URLs and automatically starts from the next unwatched one.

Why is the array reversed?

The script processes the list from its last entry to its first (original index -1 → 0), as specified for this migration — so if your scrape was newest-first, playback effectively runs in chronological order.

Why domcontentloaded and not networkidle?

YouTube keeps streaming, telemetry, and social sockets open for as long as the page exists. networkidle requires a quiet window that effectively never arrives, so navigation would time out on most videos. domcontentloaded returns as soon as the page is usable, and the short <video> wait handles the rest.

What exactly happens to a failed URL?

The warning is logged, then the URL is inserted into watched_videos like any other — "marked as attempted" — and the loop moves on. That trade-off keeps a single 404 from stalling an 8-day run. Delete the row (see Usage) if you want a specific URL replayed.

Is the data safe / private?

Everything stays local: the JSON input, the SQLite state, and the browser profile never leave your machine. The example JSON in the repo is illustrative only — the script reads nothing but your scraped_history.json. The only network traffic is Playwright driving your own logged-in YouTube session to the URLs in your file.
